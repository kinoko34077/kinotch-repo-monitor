# Local Web UI Migration Design

## Intent

Replace the Tkinter presentation layer with a localhost Web UI while preserving the already-audited repository discovery, Git inspection, status classification, repository identity, and AppData configuration behavior.

The application remains a local observation tool. It does not infer ChatGPT generation state from a chat URL or file activity.

## Runtime architecture

```text
Browser
  │  http://127.0.0.1:<port>
  ▼
Local HTTP server
  ├─ static HTML/CSS/JS
  ├─ JSON repository snapshot API
  └─ local action API
        │
        ├─ config.py / registry.py / discovery.py
        ├─ git_inspector.py
        └─ status.py
```

The server binds to `127.0.0.1` only. No LAN/public binding is provided by the default launcher.

## Dependency policy

- Python 3.11+.
- Python standard library only at runtime.
- Git executable remains the only external runtime dependency.
- Frontend uses Vanilla HTML/CSS/JS; no Node/npm build step or framework runtime.

## Server responsibilities

`src/repo_monitor/web_server.py` owns:

- lifecycle of the localhost HTTP server;
- initial discovery/merge/save;
- repository snapshot collection using the existing bounded-parallel inspector;
- conversion of snapshots into JSON-safe view models;
- mutation endpoints for ChatGPT URL, rediscovery, registration removal and open-folder action;
- static asset serving from the package `web/` directory;
- browser-open behavior after the server has bound successfully.

It must not duplicate Git parsing, status semantics, repository identity logic or config persistence.

## HTTP surface

All API responses use JSON and include explicit HTTP status codes.

- `GET /` -> `index.html`
- `GET /app.css` -> stylesheet
- `GET /app.js` -> frontend logic
- `GET /api/state` -> current repositories, classified status, timing/config metadata
- `POST /api/rediscover` -> rediscover and persist repository registry, then return current state
- `POST /api/repos/<urlencoded-repo-key>/chat-url` body `{ "chat_url": "..." }` -> persist URL
- `POST /api/repos/<urlencoded-repo-key>/remove` -> remove registration using current rediscovery semantics
- `POST /api/repos/<urlencoded-repo-key>/open-folder` -> request the OS to open the repository directory

Unknown repositories return 404. Invalid JSON or invalid action data returns 400. Unexpected server failures return JSON 500 without exposing a Python traceback to the browser.

## Repository identity

The API key is the existing normalized local-path identity from `registry.repo_identity()`, URL-encoded by the frontend. Display name remains the repository basename.

## Refresh model

The browser polls `GET /api/state` at the configured `refresh_ms` interval. Each request performs one bounded-parallel snapshot batch with at most four Git workers. The server does not run a permanent background refresh thread or database.

This preserves the lightweight ownership model: no monitoring work occurs when no browser is requesting state.

## Web UI

The page is a responsive card dashboard:

- desktop defaults to five columns when space permits;
- CSS grid automatically reduces columns on narrower windows;
- toolbar contains title, update indicator and rediscover action;
- cards show repository name, state label, branch, short HEAD, changed count, activity age, upstream ahead/behind and Chat registration status;
- state is communicated by both text and color;
- registered ChatGPT cards open the saved URL when the primary card action is used;
- an edit control updates ChatGPT URL without browser prompts generated by the server;
- folder-open and remove-registration actions are explicit controls rather than a platform-specific right-click menu;
- errors are visible in a status area rather than silently failing.

Frontend rendering escapes data by assigning text through DOM text properties; repository data is never inserted as unsanitized HTML.

## Launcher behavior

`run.cmd` continues to be the user entry point. `python -m repo_monitor` starts the local server, selects an available loopback port from the configured/default port strategy, prints the URL, and opens the default browser unless `--no-browser` is supplied.

Headless verification uses `--smoke` and server tests without opening a browser.

## Config compatibility

Existing `config.json` remains valid. `columns` may remain for backward compatibility during v0.2 but CSS responsiveness is authoritative for actual layout. ChatGPT URLs and local paths remain outside the repository.

## Security boundary

- bind loopback only;
- no CORS wildcard;
- no shell interpolation for repository paths;
- folder-open uses direct OS APIs/subprocess argv as before;
- no endpoint edits monitored repository contents;
- no external network service is required for monitoring.

## Verification

Required evidence before merge:

1. existing core tests remain green;
2. server tests cover static assets, JSON state, malformed JSON, unknown repo, chat URL persistence, remove and rediscover actions;
3. launcher smoke no longer imports/needs Tkinter;
4. Windows CI runs the full suite and actual launcher smoke;
5. a localhost-render check confirms `index.html`, CSS and JS load and the dashboard can render representative repository JSON;
6. changed scope is re-audited before merge.

## Non-goals

- public hosting or remote access;
- multi-user authentication;
- background Windows service;
- browser extension capture;
- WebMCP/site-tools integration;
- direct ChatGPT internal-state detection.
